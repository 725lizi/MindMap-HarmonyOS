# AI 双模型协作开发策略（DeepSeek × 豆包 Seed）

> 原则：让每个模型干它最擅长的事，用明确的「数据契约」在两者之间交接，谁写的代码都要过同一套质量门。

## 1. 一句话分工

- **DeepSeek 负责「想清楚、算出来」**：树算法、结构化 JSON 生成、工具函数、文本转脑图数据。
- **豆包 Seed 代码模型负责「画出来、接得上」**：复杂 ArkTS 自定义 UI 渲染、依赖项目现有接口的业务接线。
- 两个模型互补：**DeepSeek 产出结构化数据与算法，豆包 Seed 负责鸿蒙 UI 与组件开发，整体效率最高。**

> 名词通俗解释
> - **结构化 JSON**：一种格式固定、字段明确的「数据清单」，程序可以直接读懂，不需要猜。脑图数据就是 `{id, text, children:[...]}` 这样的嵌套清单。
> - **ArkTS**：鸿蒙开发用的编程语言，可以理解为「带严格类型规矩的 TypeScript」；自定义 UI 就是用它写屏幕上看得见、能手势操作的界面。
> - **数据契约**：两个模块（或两个模型）交接数据时约定好的固定格式，相当于「交接单模板」，谁都不许私自改格式。

## 2. 任务路由表（拿到需求先查这张表）

| 任务类型 | 交给谁 | 本项目对应位置 | 为什么 |
|---|---|---|---|
| 树形布局算法（节点坐标、紧凑树、轮廓合并） | ✅ DeepSeek | `library/.../layout/` | 纯算法、输入输出明确，DeepSeek 推理与边界情况覆盖强 |
| 树模型的增删改查、遍历、深度/路径计算 | ✅ DeepSeek | `library/.../model/` | 标准数据结构问题，不依赖鸿蒙 SDK |
| 序列化/校验/容错（JSON 往返、非法输入分类） | ✅ DeepSeek | `library/.../export/JsonSerializer` | 规则明确、可枚举错误码、易写单测 |
| 纯工具函数（坐标换算、id 生成、格式化） | ✅ DeepSeek | 各层 `utils` | 无 UI、无系统 API 依赖 |
| 「一段文本/笔记 → 脑图树 JSON」 | ✅ DeepSeek（运行期也是它） | FocusTimer 业务层 Prompt + 解析 | 大模型本职：理解语义并输出固定结构 |
| 视口状态机这类「纯计算但要贴合手势体验」 | ✅ DeepSeek 出算法，豆包接线 | `gesture/` 算法 + `render/` 手势绑定 | 计算与 UI 分开，交接点是状态字段 |
| MindMapView 自定义渲染（Canvas 连线、节点卡片、叠加层） | ❌ 豆包 Seed | `library/.../render/MindMapView.ets` | 强依赖 ArkUI 组件签名与 API 24 的 .d.ts，DeepSeek 知识容易过时（本次 textOverflow 报错就是例子） |
| 手势系统与组件绑定（Pinch/Pan/Tap、GestureGroup） | ❌ 豆包 Seed | `render/` + `gesture/` 的 UI 侧 | ArkUI 手势 API 细节多、版本差异大 |
| 依赖项目现有接口的业务调用（怎么调 EditController、怎么接现有页面路由、怎么用现有主题） | ❌ 豆包 Seed | entry Demo、FocusTimer 接入层 | 需要读项目上下文，豆包代码模型对工程内代码理解更准 |
| 编译报错/类型不匹配修复（10505001 这类 SDK 签名问题） | ❌ 豆包 Seed | 报错文件 | 以本机 SDK `.d.ts` 为唯一事实来源，不靠记忆 |
| 主题渲染、动画、属性链式调用 | ❌ 豆包 Seed | `render/`、`theme/` 接线 | 通用属性签名随 API 版本变，必须查本机声明 |

## 3. 三问判断法（拿不准时按顺序问自己）

1. **这段代码离开鸿蒙 SDK 能不能独立运行、能不能用 Node 离线测？** 能 → DeepSeek；不能（要 import 系统 Kit / ArkUI 组件）→ 豆包。
2. **它的产出是不是一份「固定格式的数据」？** 是 → DeepSeek。
3. **它是不是要「对着项目里已有的接口/页面/组件」写接线？** 是 → 豆包。

## 4. 标准协作流水线（一个功能怎么在两个模型间流转）

```
需求（豆包侧先出需求卡：现象/契约/验收/边界）
   │
   ├─ 算法与数据部分 → DeepSeek
   │     输入：数据契约 + 输入输出示例 + 边界情况清单
   │     产出：纯逻辑代码 + 期望值清单（黄金用例）
   │
   ├─ 交接：把 DeepSeek 产出套进项目的数据契约，补本地单测（Hypium），全绿才放行
   │
   └─ UI 与接线部分 → 豆包 Seed
         输入：已锁定的契约 + 本机 SDK .d.ts 签名 + 现有组件接口
         产出：ArkUI 组件/页面接线，编译 0 error，真机/预览器看效果
```

> Hypium：鸿蒙官方的单元测试框架，相当于「自动批改作业的老师」，我们用它离线验证纯逻辑对不对（现在已有 65 个用例）。

## 5. 给两个模型的提示词要点

**给 DeepSeek（算法/数据）时必须附：**
- 数据契约（字段名、类型、可否为空、嵌套结构）；
- 2~3 个输入→输出示例，含 1 个异常输入；
- 明确「不要 import 任何鸿蒙/系统库，输出纯函数风格」；
- 要求同时给出可独立验证的期望值，而不是只给实现。

**给豆包 Seed（UI/接线）时必须附：**
- 对应本机 SDK 版本（6.1.1 / API 24）与报错原文；
- 现有组件的 props/方法签名、相关文件路径；
- 「以本机 .d.ts 声明为准，不许凭记忆写 API 签名」；
- 不许改动数据契约与纯逻辑层、不许引入网络/AI 依赖。

## 6. 不管谁写，都要过的质量门

1. **纯逻辑必须可离线单测**：算法/工具函数进 `src/test`，期望值独立推算，用例数只增不减（当前 65）。
2. **UI 必须以本机 SDK 为准**：凡是组件属性/系统 Kit 签名问题，查 `.d.ts`，不接受「我记得是这样」。
3. **library 红线**：组件库内零网络、零 AI 调用——注意区分两件事：
   - 「不用 DeepSeek *写* UI 代码」是**开发分工**；
   - 「组件库运行时不*调用* AI」是**架构边界**（AI 调用永远在上层 FocusTimer）。
4. **契约单点修改**：数据结构要改，先改契约文档和 `JsonSerializer`，再让两侧同时对齐，禁止 UI 层私自造字段。
5. 小步提交、每次构建 0 error；保留的 deprecation 告警要登记原因，不允许无声忽略。
